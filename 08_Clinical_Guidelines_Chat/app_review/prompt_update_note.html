Eswatini guideline chat · proposal

Why we should update the answer prompt and a few app settings

The chat often lists sources instead of answering, sometimes ignores the right passage, and occasionally repeats itself. Most of this traces to two instruction sets that contradict each other, plus default settings that suit a larger model. The fixes are small and need no new hardware.

What we have been seeing

  1. Source-by-source answers. "One guideline says X, the other says Y" instead of one answer to the question.
  2. Right passage retrieved, then ignored. Asked who should be screened for cervical cancer, the search found the right NCDIMH and HIV 2022 passages, but the answer did not use them.
  3. Repeated lines. The same sentence written over and over in one answer.

The chunks behind these answers were checked against the PDFs page by page in a separate quality pass; the cervical screening passages, for example, are complete and correct. So the problem is in how the model is instructed and run, not in the documents.

Main cause: the model gets two rulebooks that disagree

Each answer is generated from the prompt file guideline_rag_system_prompt.md plus a "response contract" that app.py appends after it. The two were written at different times and conflict on basic points. A small model (Llama 3.1 8B) cannot reconcile them and follows whichever rule it happens to weight.

TopicPrompt file saysApp contract says
Answer formatJSON with type, matched_row, quote… and all 4 examples use itkind + blocks, which the app enforces; the examples' format can never be returned
CitationsWrite document name and pageNever write them; cite source numbers only
2022 vs 2024 HIV guidance"Show both… do not pick one"Follow the precedence note: the 2024 Amendment wins
Missing patient detailsAsk first; give no regimenAnswer for each group, ask only if no subject at all
Tables"If a table looks garbled, say so instead of interpreting"Answer from any excerpt that contains the answer

How this maps to the bugs: the "show both" rule and its example teach exactly the source-by-source pattern (bug 1). The "ask first" and "garbled table" rules push the model away from answering from tables and flowcharts, which is where the cervical screening criteria are (likely bug 2). The prompt also still contains unfilled placeholders such as "[quote from document 1]".

Contributing causes in the settings

  • Repetition (bug 3): the app runs the model at temperature 0 with forced JSON output. That combination is known to send 8B models into loops. A small temperature with a fixed seed keeps answers repeatable and largely stops the loops; a code check can reject any answer that repeats a sentence and retry.
  • Possible context overflow: the context is 16,384 tokens, but one request can carry the prompt, 16 history messages, and 8 retrieved passages expanded to whole sections. When it overflows, Ollama silently drops the beginning, which is the system prompt. We are not logging the size, so we cannot yet tell how often this happens.
  • Terminal and web differ: the terminal chat sends 8 passages to the model, the web app sends 5, so a bug seen in one may not reproduce in the other.
  • STI 2026 draft flag: the document is registered as not-a-draft, so the "approval unconfirmed" notice never appears.

What I propose

  1. Replace the prompt with one consistent version (draft ready): about a third of the length, written for the format the app enforces. It keeps the useful parts (numeric checklist, safety, scope) and adds an explicit rule to answer by topic, not by source, plus two worked examples checked against the guidelines.
  2. Shorten the app's response contract to the format and calculation rules only, so the two no longer overlap.
  3. Change the generation settings (temperature 0.2, fixed seed) and add the repeated-sentence check.
  4. Log the prompt size and warn near the limit; trim history and passages if it fires.
  5. Pin the retrieval settings in .env (5-6 passages) so terminal and web behave the same; fix the STI draft flag.

All of these are text and settings changes in two files. Nothing is changed in the running app until we agree. The draft prompt and the code snippets are on the project branch in 08_Clinical_Guidelines_Chat/app_review/.

Should we change the model?

Combining several sources into one answer is the specific skill where 8B models are weakest, so a better model would likely help more than any prompt. Our g4dn.2xlarge has one NVIDIA T4 with 16 GB of GPU memory. Llama 3.1 8B uses about 5 GB of it, so there is room for a stronger model without new hardware.

Model (Ollama)Fits on the T4?Notes

27B models and largerNoDo not fit in 16 GB with our context.

Switching needs no code change: ollama pull qwen2.5:14b, set LLM_MODEL in .env, and rerun the problem questions. ollama ps confirms it runs fully on the GPU. If memory is tight, Ollama's 8-bit context cache (OLLAMA_FLASH_ATTENTION=1 and OLLAMA_KV_CACHE_TYPE=q8_0 on the server) roughly halves the context memory.

A hosted model (for example through AWS Bedrock, since we are already on AWS) would be stronger still, but questions would leave our server. The app already strips patient identifiers, but this needs a data-governance decision before we consider it.

How we would test it

  1. Collect 30-50 real questions with known answers, including the three failures above, the earlier ANC p.180 and HIV p.190 cases, and dose/threshold questions.
  2. Run them on the current setup with --sources to record what was retrieved and answered.
  3. Apply the prompt and settings changes; rerun. Then try qwen2.5:14b; rerun.
  4. Compare: correct answer, right group, cited correctly, no source-by-source listing, no repetition, response time.

Recommended order: prompt and settings first (cheap, no hardware change), then the model swap, judged on the same questions.
